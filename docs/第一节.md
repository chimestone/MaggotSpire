# 一. 第一节目标：让游戏发现并加载最小 Mod

本节目标不是修改游戏逻辑，而是建立一条可以验证的最小 Mod 加载链。

完整链路为：

```text
Entry.cs
   |
   v
dotnet build
   |
   v
MaggotSpire.dll
   |
   v
MaggotSpire.json
   |
   v
mods\MaggotSpire
   |
   v
游戏发现 Mod 并加载 DLL
   |
   v
[ModInitializer] 调用 Initialize
   |
   v
Log.Info 输出初始化日志
```

这条链路可以分成三个问题：

- 源代码能否被编译为 DLL
- DLL 与 Mod 清单能否被部署到游戏指定位置
- 游戏能否发现清单、加载 DLL 并调用入口方法

# 二. 开发环境检查

## 1. .NET 9

项目使用：

```xml
<TargetFramework>net9.0</TargetFramework>
```

因此需要安装可用的 .NET 9 SDK。检查命令：

```powershell
dotnet --version
```

本次环境中的版本为：

```text
9.0.306
```

这里需要的是 SDK，而不只是运行时。SDK 负责还原项目、调用编译器并生成 DLL。

## 2. Godot Mono/.NET 版本

本项目使用 Godot 的 .NET SDK：

```xml
<Project Sdk="Godot.NET.Sdk/4.5.1">
```

对应的 Godot 应当是 Mono/.NET 版本，而不是只能运行 GDScript 的标准版本。本次使用：

```text
D:\Soft\Godot\Godot_v4.5.1-stable_mono_win64\Godot_v4.5.1-stable_mono_win64.exe
```

Godot 版本与项目 SDK 版本保持一致，可以减少构建时的兼容问题。

## 3. 游戏程序集

项目需要引用游戏已有的程序集：

```text
D:\STEAM\steamapps\common\Slay the Spire 2\data_sts2_windows_x86_64\sts2.dll
D:\STEAM\steamapps\common\Slay the Spire 2\data_sts2_windows_x86_64\0Harmony.dll
```

其中：

- `sts2.dll` 提供游戏本体中的类型与接口，使 Mod 代码可以引用游戏 API
- `0Harmony.dll` 是项目当前准备引用的补丁库程序集

本节只确认这些程序集存在且能被项目引用，不展开 Harmony Patch 的工作方式。

# 三. 三个核心文件的职责

## 1. MaggotSpire.csproj

`.csproj` 是 C# 项目的构建说明书，主要声明：

- 使用哪个 SDK
- 目标 .NET 版本
- 源码如何参与编译
- 引用哪些外部程序集
- 构建完成后执行哪些操作

核心配置包括：

```xml
<Project Sdk="Godot.NET.Sdk/4.5.1">
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
    <LangVersion>13.0</LangVersion>
  </PropertyGroup>

  <ItemGroup>
    <Reference Include="sts2">
      <HintPath>$(Sts2DataDir)\sts2.dll</HintPath>
      <Private>false</Private>
    </Reference>
    <Reference Include="0Harmony">
      <HintPath>$(Sts2DataDir)\0Harmony.dll</HintPath>
      <Private>false</Private>
    </Reference>
  </ItemGroup>
</Project>
```

`HintPath` 告诉编译器去哪里寻找程序集。`Private=false` 表示构建时不把游戏本身已有的 DLL 再复制进 Mod 输出目录。

因此，`.csproj` 主要回答：

> 这份源码应当如何被构建？

## 2. MaggotSpire.json

`MaggotSpire.json` 是游戏发现 Mod 时读取的清单文件。它用于描述 Mod 身份及需要加载的 DLL。

它与 C# 编译不是同一个阶段：编译器通常不依靠该 JSON 理解 `Entry.cs`，但游戏的 Mod 加载器需要依靠它发现 Mod。

因此，JSON 主要回答：

> 这个目录是不是一个 Mod，以及游戏应当加载什么？

## 3. Entry.cs

`Entry.cs` 提供最小初始化入口：

```csharp
using MegaCrit.Sts2.Core.Logging;
using MegaCrit.Sts2.Core.Modding;

namespace MaggotSpire;

public static class Entry
{
    [ModInitializer]
    public static void Initialize()
    {
        Log.Info("[MaggotSpire] Mod initialized successfully.");
    }
}
```

其中：

- `Entry` 是入口类，本身不需要实例化
- `[ModInitializer]` 标记游戏加载 Mod 后应调用的方法
- `Initialize()` 是初始化方法
- `Log.Info(...)` 在日志中留下可检查的运行证据

因此，`Entry.cs` 主要回答：

> 游戏加载 DLL 后，Mod 从哪里开始执行？

# 四. restore 与 compile 的区别

## 1. restore

`restore` 是“准备构建依赖”的阶段。

```powershell
dotnet restore
```

它会读取 `.csproj`，解析项目所需的 SDK、包与依赖信息，并生成后续构建需要的中间文件。

它主要验证：

> 构建所需的依赖能否被找到和准备好？

## 2. compile

`compile` 是“把源码编译成程序集”的阶段。通常直接运行：

```powershell
dotnet build
```

`dotnet build` 默认会先进行必要的 restore，然后调用 C# 编译器，将 `.cs` 文件编译为：

```text
MaggotSpire.dll
```

它主要验证：

> 源码在当前引用关系下是否合法，并且能否生成 DLL？

因此：

```text
restore 成功 != compile 成功
compile 成功 != 游戏成功加载 Mod
```

这三个阶段需要分别取证。

# 五. 构建、部署与游戏加载

## 1. 构建

在项目目录运行：

```powershell
dotnet build
```

构建成功说明：

- `.csproj` 能被读取
- C# 源码通过编译
- `sts2.dll` 等编译引用能够被找到
- `MaggotSpire.dll` 已经生成

但是，此时只能证明 DLL 可构建，不能证明游戏已经看见它。

## 2. 部署

构建产物和清单需要进入游戏的 Mod 目录，形成类似结构：

```text
mods\MaggotSpire\
├── MaggotSpire.dll
└── MaggotSpire.json
```

部署的本质是让游戏在约定位置同时拿到：

- 可执行的 Mod 程序集
- 描述该 Mod 的清单

只生成 DLL 而没有部署，游戏不会自动从开发项目目录加载它。

## 3. 启动游戏

本次使用带日志的方式启动游戏，并关闭 Steam 强制依赖：

```text
--log --force-steam=off --rendering-driver opengl3
```

启动参数本身不是成功证据，它只是让日志与本地测试更容易进行。

# 六. 日志取证

## 1. 为什么要看日志

“游戏启动了”不能证明 Mod 被加载；“编译成功了”也不能证明初始化方法被调用。

真正需要检查的是一条逐层成立的证据链：

```text
发现 MaggotSpire.json
   |
   v
根据清单找到 MaggotSpire.dll
   |
   v
加载 MaggotSpire.dll
   |
   v
发现 [ModInitializer]
   |
   v
调用 Initialize()
   |
   v
出现自定义 Log.Info 日志
```

## 2. 本次有效证据

日志中确认了以下现象：

```text
找到 Mod manifest
加载 MaggotSpire.dll
调用 Mod initializer
[MaggotSpire] Mod initialized successfully.
RUNNING MODDED
```

其中最关键的是自定义日志：

```text
[MaggotSpire] Mod initialized successfully.
```

它证明执行已经进入自己编写的 `Initialize()`，而不仅是游戏扫描到了某个文件夹。

# 七. 关于删除 JSON 的纠正

## 1. 原先容易混淆的判断

容易产生这样的推断：

> 如果删除 `MaggotSpire.json` 后项目仍能 `dotnet build`，那么 JSON 可能没有作用。

这个判断混淆了编译阶段和游戏发现阶段。

## 2. 正确结论

删除 JSON 后，C# 编译仍然可能成功，因为：

- 编译器主要读取 `.csproj` 和 `.cs` 文件
- JSON 不负责定义 `Entry` 类，也不参与 C# 语法检查
- DLL 仍然可以被正常生成

但是游戏将无法通过 Mod 清单发现并识别这个 Mod。因此：

```text
删除 MaggotSpire.json
        |
        +--> dotnet build 仍可能成功
        |
        +--> 游戏无法正常发现 MaggotSpire Mod
```

准确表述应当是：

> `MaggotSpire.json` 不决定源码能否编译，但决定游戏能否按照 Mod 加载规则发现并加载该 Mod。

这也是为什么验证不能停在 `dotnet build`，而必须继续检查部署目录与游戏日志。

# 八. 第一节结论

本节建立了最小 Mod 的完整验证流程：

```text
检查 .NET 9 与 Godot Mono/.NET
   |
   v
确认 sts2.dll 与 0Harmony.dll
   |
   v
使用 .csproj 构建 Entry.cs
   |
   v
生成 MaggotSpire.dll
   |
   v
将 DLL 与 MaggotSpire.json 部署到 mods\MaggotSpire
   |
   v
启动游戏并读取日志
   |
   v
确认 [ModInitializer] 调用了 Initialize
```

三个文件各自承担不同职责：

| 文件 | 职责 |
|---|---|
| `MaggotSpire.csproj` | 描述项目如何还原、引用和编译 |
| `MaggotSpire.json` | 让游戏发现并识别 Mod |
| `Entry.cs` | 提供 Mod 被加载后的初始化入口 |

最终结论是：

$$
\boxed{\text{编译成功}\neq\text{部署成功}\neq\text{游戏加载成功}}
$$

只有在日志中看到自定义初始化信息，才能确认最小 Mod 加载链真正闭合。
